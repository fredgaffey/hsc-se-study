4.24 Effectiveness

Syllabus

Evaluate the effectiveness of a software engineering solution, including:

  • developing a report to synthesise feedback
  • developing a test plan
  • testing data used/generated based on path and boundary testing
  • comparing actual output with expected output

  Learning Intention and Success Criteria

Learning Intention - Students will:

  • To evaluate the effectiveness of a software engineering solution by synthesising feedback, developing a test plan, applying path and boundary testing, and comparing actual versus expected outcomes.

Success Criteria - Students can:

  • Develop a structured report that synthesises feedback from stakeholders.
  • Create a comprehensive test plan covering all relevant scenarios.
  • Apply path and boundary testing techniques to evaluate software robustness.
  • Accurately compare actual output with expected output to assess the solution's performance.

  Content

An effective software evaluation begins by gathering feedback from a range of stakeholders. This feedback offers valuable insights into how the software performs from different perspectives, such as user experience, performance, and feature implementation.

Synthesising Feedback:

Once feedback is gathered, it must be synthesised into a clear, actionable report. The report should:

  1. Categorise feedback into relevant sections (e.g., user experience, performance, functionality).
  2. Prioritise feedback based on severity or frequency of issues. A common approach is to categorise issues as critical, high, medium, or low priority.
  3. Provide action items based on feedback, such as recommendations for further testing, redesign, or feature modification.
Effectiveness: Test Plan
Effectiveness Criteria:

  • Completeness: Includes all functional and non-functional requirements.

    • Effectiveness: Ensures no critical feature is left untested.

  • Accuracy & Reliability of Tests: Produce consistent and reproducible results?

    • Effectiveness: Prevents false positives/negatives, ensuring reliable test outcomes.

  • Testing Environment: 

    • Performance Testing: Stress, load, and performance testing?
      • Effectiveness: Ensures software stability under peak usage conditions.

    • Real-World Simulation: Replicates high traffic, concurrent users, and hardware variations.
      • Effectiveness: Confirms system resilience and scalability.

  • Test Execution Time & Resource Usage

    • Optimised Execution: Avoids redundant or slow-running tests.

      • Effectiveness: Speeds up testing without compromising coverage.

    • Resource Efficiency: Minimises CPU, memory, and network overhead.

      • Effectiveness: Prevents performance bottlenecks during testing cycles.
Effectiveness: Path Testing
Effectiveness Criteria: 

  • Test Coverage: Ensure all logical paths in the program are executed at least once.

    • Effectiveness: Detects missing logic, dead code, and untested execution flows.

  • Boundary Testing: Focuses on edge values rather than general inputs.

    • Effectiveness: Identifies off-by-one errors, overflow issues, and incorrect condition handling

  • Comprehensive Testing Data:

    • Effectiveness: Uses a mix of valid, invalid, extreme, and edge case inputs to test system reliability.
Effectiveness: Synthesis Report
Effectiveness Criteria: 

  • Accuracy of Feedback Aggregation: Collects, categorises, and summarises feedback

    • Effectiveness: Ensures feedback is grouped correctly without misclassification or data loss.

  • Relevance & Quality of Insights: Extracts key trends and actionable insights from feedback.

    • Effectiveness: Avoids generating overly generic or irrelevant summaries.

 

Developing a Test Plan

A test plan is essential for systematically evaluating the functionality, performance, and reliability of the software. The test plan should be comprehensive, covering all critical aspects of the solution.

Components of a Test Plan:

  • Scope: Clearly defines what features and functionalities are being tested, as well as any areas that will not be covered in this round of testing. This ensures focused and efficient testing.

  • Objectives: Outline what the testing seeks to achieve, such as verifying that the system meets performance benchmarks or that the user interface behaves correctly under different conditions.

  • Test cases: Individual scenarios to be tested, often based on user stories or specific functional requirements. Each test case should include:

    • Preconditions: The state of the system before the test is run.

    • Test data: Input values required to execute the test.

    • Steps: The sequence of actions to perform the test.

    • Expected outcome: What should happen when the test is executed.

    • Example: For a password reset feature, a test case might involve the following:

      • Precondition: The user must have an account.
      • Test data: Email address associated with the account.
      • Steps: Request password reset, enter email, receive reset link, enter new password.
      • Expected outcome: User is redirected to the login page, and the password reset email is successfully delivered.

  • Test environment: Specifies the hardware, software, and network configurations under which the tests will be executed, ensuring consistency and accuracy in results.

  • Test criteria: Define success or failure for each test case. For example, a pass might be logged if the system behaves exactly as described in the expected outcomes, while deviations would be logged as failures.

Path and Boundary Testing

Path testing and boundary testing are key techniques for ensuring that a software solution behaves correctly under various conditions.

Path Testing:

Path testing involves exploring the different execution paths within a software system to ensure that all logic flows and decision points are correctly implemented. This is particularly useful for condition-heavy code, such as authentication systems or decision-making algorithms.

  • How it works: In path testing, testers identify all possible paths a user might take through the software. For each path, they create test cases to ensure that every branch and conditional statement in the code is executed at least once.

    • Example: A payment system that checks for available funds, verifies the user's identity, and processes the payment must have tests for paths where the payment succeeds, paths where the payment fails due to insufficient funds, and paths where the user authentication fails.

Boundary Testing:

Boundary testing focuses on edge cases—the extreme ends of input values. These are often the points where software can fail due to overlooked assumptions or insufficient validation.

  • How it works: Testers design inputs that lie just inside and outside the boundary values of input ranges. By doing so, they assess how the software behaves when pushed to its limits.

    • Example: For a form field requiring a username between 5 and 15 characters, boundary tests would include:
      • Valid inputs: 5 characters, 15 characters.
      • Invalid inputs: 4 characters, 16 characters.

    Boundary testing is crucial in identifying issues like array overflows, incorrect validation, or performance degradation under extreme input conditions.

Comparing Actual Output with Expected Output

Once testing is complete, it’s essential to compare the actual output of the software with the expected output defined during the test planning phase. This step helps validate the correctness of the solution and identify discrepancies that indicate bugs or unmet requirements.

Key Comparison Steps:

  • Capture actual output: During the execution of test cases, record the system’s behaviour. This could involve logging error messages, system responses, database states, or interface behaviours.

  • Compare against expected outcomes: For each test case, the actual results are compared to the expected outcomes to verify correctness.

    • Example: For a login system:
      • Test case: User enters correct credentials.
      • Expected output: System redirects to the dashboard.
      • Actual output: If the user is instead redirected to an error page, there is a discrepancy that needs addressing.

  • Document discrepancies: If the actual and expected outcomes differ, document the details for further investigation. Each discrepancy should be classified according to its severity (e.g., critical, high, medium, low) and assigned to a development team for resolution.

Regression Testing:

If fixes are applied, it’s important to conduct regression testing to ensure that the changes do not introduce new issues elsewhere in the software. This process involves re-running relevant test cases to verify the integrity of the overall system after modifications.
