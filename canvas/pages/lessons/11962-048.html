  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Students will understand the process of designing code in an OOP language, including task definition, top-down and bottom-up approaches, the facade pattern, and agility in development.

Success Criteria - Students can:

  • Students can define coding tasks, apply design approaches, implement the facade pattern, and adapt their code to changing requirements efficiently.

  Content

The process of designing software in an object-oriented programming (OOP) language is essential for creating systems that are clear, scalable, and easy to maintain. Effective design ensures that code meets user requirements while adhering to best practices. This process involves defining tasks, choosing appropriate design approaches such as top-down or bottom-up, implementing design patterns like the facade pattern, and adopting agile principles to accommodate change.

 

Code Design

The main advantage of object-oriented programming over imperative programming is its unique ability to create elegant and beautiful software through a design that is centred around the use of objects; rather than functions used in procedural programming.

Throughout the remainder of this unit, the aim is to emphasise good design practices of object-oriented code as we apply the principles you have learned to effectively create modular systems that are flexible, maintainable and reusable.

When it comes to code design, there is no clear right or wrong answer. There are many shades of grey, where design decisions aren't clear cut. Good programming skill doesn't matter if you don't have good design. Designing elegant OOP software is an art.

Task Definition

A task definition (or problem statement) is a concise and clear description of a specific issue or challenge. It acts as a foundational element in the problem-solving process by clearly articulating what needs to be addressed. A well-crafted task definition should be focused, precise, and actionable, enabling individuals or teams to remain aligned on the objective and work collaboratively toward a solution.

Key Characteristics of a Good Task Definition

  1. Clarity: The problem should be easy to understand and free from jargon.
  2. Focus: It should highlight the core issue without unnecessary details.
  3. Importance: The statement should explain why solving the problem matters, emphasizing its significance.
  4. Impact: Identifies who or what is affected by the issue.
  5. Stimulates Creativity: Inspires innovative and critical thinking to develop effective solutions.

Top-Down and Bottom-Up

The Top-Down and Bottom-Up design methodologies represent two different approaches to system development.

  • Top-Down Design is an approach where the system is broken down into smaller components starting from the highest level.
    • In OOP, we would start by creating high-level generalised classes before creating lower-level child classes that have more specific responsibilities.
    • e.g. In a game, we may start by creating a generalised Character class before creating more specific child classes such as Knight and Witch.
  • Bottom-Up Design is an approach where the system is built starting from the lowest level components.
    • In OOP, we would start by creating low-level classes with specific responsibilities before generalising into higher-level parent classes.
    • e.g. In a game, we may start by creating the Knight and Witch classes before creating more a generalised Character class.

Façade Pattern

In software design, there are many established design approaches that are used as a template for handling common design problems. One such problem is having to deal with complexity of our object-oriented code. The solution is to create a simplified interface (facade) to hide the complexity of underlying classes in a way that allows people who are unfamiliar with the code (e.g. the client) to use the software.

The Facade Pattern is a design approach that provides a simplified interface to a complex subsystem. It is particularly useful when you have a program with multiple interdependent classes, and you want to make it easier to use by providing a single interface to interact with that system.

Imagine your computer as one of these complex systems. The facade in this scenario is your keyboard, mouse and screen which offer you a method to control and use your computer whilst hiding the complexity and millions of operations going on behind the screen to provide you with a user friendly method to interact with the systems.

Example:

Consider a home entertainment system with:

  • A DVD Player
  • A Projector
  • Lights
  • A Sound System

To use the Facade Pattern in the design of this system, we can provide a simple interface class called RemoteControlFacade to interact with the components of the home theatre without knowing how to use each of those individual components.

The attributes of the RemoteControlFacade class contains the objects that make up the home theatre.

The methods of the RemoteControlFacade class then call the methods of those objects (dim(), on(), set_input(), set_volume(), etc).

We can then use the interface methods in the RemoteControlFacade to start and end a movie without needing to know how to use the DVDPlayer, Projector, Lights or SoundSystem classes. The client only needs to know how to use the facade interface.

Output:

Get ready to watch a movie...
Lights dimmed to 10%.
Projector is on.
Projector input set to DVD.
Sound system is on.
Sound system volume set to 5.
DVD Player is on.
Playing movie 'Imitation Game'.
Shutting movie theater down...
DVD Player is off.
Sound system is off.
Projector is off.
Lights dimmed to 100%.

 

Agility

When designing object-oriented code, it is important to structure classes in a way that allows for easy and efficient modification.

The agility of a program is described as its ability to adapt to unspecified or changing needs of the client.

This adaptability is crucial in modern software development, where requirements can evolve rapidly.

If adding a feature requires a large number of classes to be modified, then:

  • the update will take a long amount of time
  • the large number of modifications will likely cause existing features to fail

This is a sign of poorly designed OOP code.

However, if the same feature can be added by modifying a small number of classes, then:

  • the update will take a short amount of time
  • the small number of modifications will not largely affect existing features

This is a sign of effectively designed OOP code.

Ideally, when we need to add new features into our object-oriented code, these changes should only be made in as few places as possible. If you need to make changes in many other places too, then program development will become much more complicated and expensive as a result because of poor agile design.

Example:

Consider a video game that has to be frequently updated to receive new characters. If we have a generalised character class that contains the common attributes and behaviours across all characters in the game (e.g. moving, attacking, defending), then any modifications that add any new characters into the game will mainly require the addition of a single new child class and its specialised behaviours. The more changes that are required outside of the new child class, the less agile the object-oriented code becomes.
