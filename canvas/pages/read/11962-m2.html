1.6 Modelling tools

Syllabus
Use modelling tools including structure charts, abstraction and refinement diagrams to support top-down and bottom-up design

  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Understand the purpose and benefits of modelling tools in software design.

Success Criteria - Students can:

  • Explain the purpose of modelling tools in software design and provide examples of their use.
  • Create and interpret structure charts, abstraction diagrams, and refinement diagrams to represent software systems.

  Content

Abstraction and refinement are two key concepts in software design that play complementary roles in modelling systems with complex requirements.

 

   Key Terminology

  • Abstraction - The process of simplifying complex systems by only focusing on the essential aspects while ignoring irrelevant details. It involves creating a model that captures the essential characteristics of a system.

    Abstraction helps manage complexity by hiding unnecessary details and exposing only what is relevant to a particular level of design or understanding.

  • Refinement - The process of elaborating and adding details to a less detailed or abstract representation. It involves breaking down a high-level abstraction into more concrete and detailed components.

    Refinement is necessary for translating abstract designs into concrete implementations. It allows developers to gradually specify the details needed to implement and program a system.

 

Relationship between Abstraction and Refinement

Abstraction and refinement are interconnected processes in the software development life cycle.

Initially, you start with high-level abstractions to understand and conceptualise the system.

As you progress, you refine these abstractions, adding details and specificity to move closer to an implementable and programmable solution.

In summary, abstraction is about simplifying complexity by creating higher-level models, while refinement is about adding details to these models to make them implementable. Both are essential in designing and building robust, manageable and maintainable software systems.

Abstraction helps stakeholders, including clients and programmers, to grasp the overall concept of the software without getting too bogged down in details. Refinement ensures that the abstract design can be translated into a practical, functional, and structurally sound software solution.

 

Example

Imagine you are an architect tasked with designing a new office building.

At the beginning of the project, you need to create a high-level abstract conceptual design that captures the essential features of the building, such as:

  • its overall layout
  • the number of floors
  • the general purpose of each space (offices, meeting rooms, etc.).

This high-level design represents an abstraction of the final building, ignoring specific construction materials, detailed interior design, and other intricate details.

As the project progresses, the high-level design needs to be refined to provide more detailed specifications for construction. Refinement involves breaking down the abstract design into concrete details.

For example, you would refine the design by specifying the types of materials to be used for the foundation, walls, and roof. You would also detail the interior design, specifying the layout of each office, the materials for flooring, and the colour scheme.

 

Top-Down and Bottom-Up Design

 

Top-Down

Top-down design, starts with the high-level system overview and then progressively breaks it down into smaller, more detailed components.

  1. Begin with a broad understanding of the entire system
  2. Decompose the system into subprograms or modules
  3. Further break down each subprogram into smaller modules until reaching a level where the modules are manageable and can be easily implemented

Advantages

  • Provides a clear and structured view of the entire system from the beginning.
  • Allows for a better understanding of the system's architecture and organisation.
  • Supports early identification of major components and interactions.

Challenges

  • Requires a thorough understanding of the entire system upfront.
  • May result in delays in getting started with actual implementation.

Bottom-Up

Bottom-up design, starts with the implementation of small, individual components or modules and gradually combines them to create larger systems.

  1. Begin by implementing small, independent modules or subprograms.
  2. Combine these modules to create larger, more complex subprograms.
  3. Continue the process of combining subprograms until the entire system is constructed.

Advantages

  • Allows for early and incremental implementation, providing quicker results.
  • Developers can focus on specific, isolated functionalities without needing a complete understanding of the entire system.
  • Easier to adapt to changes as development progresses.

Challenges

  • May lead to a lack of a cohesive overall system view until later in the development process.
  • Integration challenges may arise when combining independently developed components.

 

Structure Chart

A structure chart is an abstracted graphical representation of a software system by showing the separate modules or subroutines that comprise the system and their relationship to each other.

 

Structure Charts can be seen as an extension of Abstraction and Refinement Diagrams. Abstraction and Refinement Diagrams, also called hierarchy charts, are a simple way to show the design of a program. They represent the program in smaller, manageable parts, either from top-down or bottom-up. Each part, or module, is usually numbered to show its position within the overall structure of the design.

 

They are represented as a hierarchical diagram, where the top level represents the system as a whole, and each subsequent level represents increasingly detailed and refined components of the system. Each component in the structure chart is represented by a rectangular box, and the relationships between components are shown by lines connecting the boxes.

Structure charts are particularly useful for breaking down a large and complex system into smaller, more manageable pieces, and for identifying the relationships and dependencies between those pieces.

Further refinement for each of the lower-level subroutines can be shown in a separate structure chart, using the same name as the subroutine that you are refining in the main structure chart.

The chart is read from top to bottom, with component modules or subroutines on successively lower levels, indicating these modules or subroutines are called by the module or subroutine above.

For all modules or subroutines called by a single module or subroutine, the diagram is read from left to right to show the order of execution.

1.7 Logic and structure

Syllabus
Analyse the logic and structure of written algorithms including
- determining inputs and outputs
- determining the purpose of the algorithm
- desk checking and peer checking
- determining connections of written algorithms to other subroutines or functions

  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Analyse the logic and structure of written algorithms by identifying inputs, outputs, and purposes, as well as to engage in desk checking and peer checking processes to ensure connections with other subroutines or functions are understood.

Success Criteria - Students can:

  • Accurately identify inputs and outputs in a given algorithm.
  • Clearly understand and articulate the purpose of the algorithm.
  • Effectively perform desk checking to verify the correctness of the algorithm.
  • Engage in peer checking to receive and provide feedback on algorithm logic and structure.
  • Demonstrate the ability to determine how the algorithm connects with other subroutines or functions within a program.

  Content

Analysing algorithms to understand their logic and structure is a fundamental skill in software engineering. It involves understanding how a set of instructions (the algorithm) solves a particular problem. A well-analysed algorithm ensures efficiency, clarity, and effectiveness in solving problems.

 

Inputs and Outputs

  • Inputs: These are the data or variables that are fed into an algorithm. Understanding inputs is crucial as they directly affect how the algorithm operates.
  • Outputs: These are the results produced by the algorithm. Knowing the desired output helps in shaping the steps of the algorithm.

Algorithm Purpose

  • This involves understanding what the algorithm is designed to achieve. Is it sorting data, solving a mathematical problem, or processing user input?
  • Understanding the purpose helps in evaluating the effectiveness of the algorithm and its suitability for a task.

Desk Checking & Peer Checking

  • Desk Checking: This is a manual process of tracing the execution of an algorithm using a sample set of inputs. It helps in understanding the flow and identifying any logical errors.
  • Peer Checking: Involves having another person (preferably a peer) review the algorithm. This collaborative approach can uncover issues that the original author might have missed.

Connections to Subroutines

  • Algorithms often interact with other parts of the software, like subroutines or functions. Understanding these interactions is crucial for ensuring the algorithm integrates smoothly into the larger system.
  • It’s important to analyse how data is passed between these components and how they affect the overall functionality.

Number Guessing Game

Given below is psuedocode for a Number Guessing Game.

BEGIN NumberGuessingGame

minNumber = 1

maxNumber = 100

attempts = 0

secretNumber = GenerateRandomNumber(minNumber, maxNumber)

Display "I have chosen a number between " + minNumber + " and " + maxNumber

REPEAT

Display "Enter your guess:"

Get userGuess

attempts = attempts + 1

IF userGuess < secretNumber THEN

Display "Too low. Try again."

ELSEIF userGuess > secretNumber THEN

Display "Too high. Try again."

ELSE

Display "Congratulations! You've guessed the number in " + attempts."

ENDIF

UNTIL userGuess = secretNumber

END NumberGuessingGame

 

1. Desk Checking and Peer Checking

  • Desk Checking: This involves manually going through the pseudocode line by line to simulate what would happen during its execution. It helps identify logical errors and ensures that the program's flow makes sense. For example, manually checking that the loop continues until the correct guess is made.
  • Peer Checking: Having another person review the pseudocode can uncover issues the original author might overlook. Peers can provide feedback on the clarity of the logic and suggest improvements or identify bugs, such as ensuring the random number generation is within the specified range.

 

2. Inputs and Outputs

  • Inputs: The inputs in this program include the user's guess (userGuess) of the secret number. These are obtained through the Input statement within the loop.
  • Outputs: Outputs consist of prompts and feedback to the user, such as asking for a guess, indicating whether the guess is too low or too high, or congratulating the user upon a correct guess. The output also includes the number of attempts made to guess the correct number.

 

3. Determining Connections of Written Algorithms to Other Subroutines or Functions

  • The main program connects to the RandomNumberGenerator module through the GenerateRandomNumber(min, max) function. This function is essential for generating the secret number that the user tries to guess. It demonstrates how subroutines or modules can be utilised within a larger program to perform specific tasks, in this case, generating a random number within a defined range.

 

4. Purpose of Algorithm

  • The primary purpose of this algorithm is to create an interactive number guessing game where the user attempts to guess a randomly generated number within a certain range.

  Content

Procedures and functions are both types of subroutines and are important components of an algorithm, allowing for modularisation and code reusability. They help break down complex tasks into smaller, manageable units.

Both procedures and functions help to break down and divide complex algorithms into smaller and more manageable units that are easier to understand and maintain. They are used to organise code into logical sections and can be called multiple times within a program to prevent code duplication (repeated lines code).

Although procedures and functions serve similar purposes, there are some key differences between the two.

 

 Key Terminology

  • Functions - Blocks of code that take input(s), perform a specific task, and return a value. The primary purpose of a function is to produce a value based on the inputs provided, which can then be used in other parts of the program.
  • Procedures -Also known void functions, procedures are blocks of code that take input(s), perform a specific task but do not return a value. The primary purpose of a function is to only execute commands.

    • A function is a block of code that takes input(s), performs a specific task, and returns a value.

Syllabus
Determine typical errors experienced when developing code, including syntax, logic and runtime, and explain their likely causes

  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Develop the ability to recognise and explain common errors encountered during code development, including syntax, logic, and runtime errors, as well as their likely causes.

Success Criteria - Students can:

  • Correctly identify and categorise errors as syntax, logic, or runtime.
  • Analyse and explain the cause of each type of error.
  • Apply knowledge of common error causes to troubleshoot and resolve coding issues.
  • Demonstrate improved code quality by avoiding or quickly addressing typical errors during development.

  Content

Developing software involves a range of challenges and errors are common throughout the process. These errors can broadly be classified into three main types:

  • Syntax Errors
  • Logic Errors
  • Runtime Errors

Understanding and identifying syntax, logic, and runtime errors are essential skills for any programmer. By learning about these errors and their causes, you'll be better equipped to debug and improve your code.

 

Syntax Errors

  • Syntax errors occur when your code violates the rules of the programming language. In other words, you've made a mistake in the way you've written the code.
  • Common syntax errors include missing or extra punctuation (such as brackets, commas, or quotes), incorrect indentation, or using an incorrect keyword. All syntax errors will be detected as the source code is translated into machine code.
  • The translator, normally an interpreter or a compiler, is unable to understand code that contains one or more syntax errors.
  • To fix syntax errors, carefully review your code and ensure you're following the programming language's strict rules.

Logic Errors

  • Logic errors occur when your code runs without syntax errors, but it doesn't produce the expected output or behaviour. This usually happens because the code's logic is flawed, even though it's written correctly in terms of syntax.
  • Common logic errors include incorrect calculations, using the wrong variable, off-by-one errors (e.g., loops that run one too many or too few times), and incorrect conditional statements.
  • Logic errors can be more challenging to find and fix, as the program will still run, but the results will be incorrect. To fix logic errors, review your code's logic and consider using debugging tools, print statements, or test cases to help identify the issue.

Runtime Errors

  • Runtime errors occur when your program encounters a serious problem while it's running, causing it to crash or terminate unexpectedly.
  • Common runtime errors include dividing by zero, accessing an out-of-bounds index in an array, or attempting to use a null or uninitialised object or variable.
  • These errors often stem from incorrect assumptions about the input data, unexpected situations, or misuse of resources.
  • To fix runtime errors, add error handling to your code (e.g., using if-statements or try-except blocks in Python) to manage exceptions gracefully, and validate input data to ensure it meets your program's requirements.

1.10 Programming paradigms

Syllabus
Experiment with object-oriented programming, imperative, logic and functional programming paradigms

  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Explore different programming paradigms - object-oriented, imperative, logic, and functional - to understand their unique approaches and apply them in various programming situations.

Success Criteria - Students can:

  • Understand the key concepts and principles of each programming paradigm: object-oriented, imperative, logic, and functional.
  • Recognise and explain the differences and advantages of each paradigm.
  • Implement simple examples using each programming paradigm.
  • Demonstrate the ability to choose an appropriate paradigm for a given programming task.
  • Apply knowledge of different paradigms to analyse and compare existing code examples.

  Content

A paradigm refers to a way of programming thinking. It can be described as a model or philosophical/theoretical framework. A different approach under which laws, theories and generalisations are produced. We will be looking at the four major programming paradigms:

  • Imperative

  • Object Oriented

  • Logic

  • Functional

 

Von Neumann Architecture

The Von Neumann Architecture is the most common hardware architecture. This architecture stores a program in memory as a sequence of low-level instructions and executes them sequentially in a predetermined sequence inside the Central Processing Unit (CPU).

The architecture has led to the development of imperative programming languages. So far in this course, you have been programming using the imperative paradigm.

 

Imperative

Imperative programming focuses on the use of variables, assignment statements, control structures, data structures and algorithms.

An imperative language uses variables and data structures to model memory locations. The movement of this data is achieved through assignment statements and control structures. They are combined together into an algorithm to organise the procedures.

It is good at solving logical and mathematical problems using inputs, processing and outputs as distinct individual components. However, our brains work differently as they combine these components to solve more complex problems. Other paradigms can have a more natural method of solving problems.

 

Difficulty Solving Certain Types of Problems

  • Computers were initially used to solve mathematical problems. Imperative programs are not good at providing multiple answers to problems but are good at mathematical and arithmetic solutions.
  • However, real life problems cannot be solved using imperative languages (i.e. AI, Voice Recognition/Communication, Medical Diagnosis, Predictions, etc). Other paradigms are needed for solutions with a variety of outcomes and making judgements based on experience and intuition.

Need to Specify Code for Every Individual Process

  • Imperative programs require every part of the program to be written before the final product will operate correctly. Whereas other paradigms can infer a solution, run even when incomplete and react to changing needs without modification.

Difficulty of Coding for Variability

  • Imperative programs have modules that can be reused but are not an integral part of the paradigm. Imperative programs could be difficult to adapt to changing requirements.
  • Other paradigms can encourage the re-use of modules to solve similar problems and can contain a processing component that works on different sets and types of data.

Object-Oriented

Object-Oriented programming focuses on the use of objects, classes, attributes, methods, variables, control structures, instantiation, encapsulation, inheritance, polymorphism (overloading or creating variation) and abstraction.

Object Oriented languages work with objects that communicate with each other using methods. Each object is a separate entity that is part of a class of objects. Subclasses can be created using inheritance. Objects also use encapsulation which is hiding the data from other objects.

Object oriented languages are excellent for creating encapsulated code that is very easily reused in other applications, and is easily tested for bugs.

Classes

  • A Class outlines a template from which Objects are created, like a technical blueprint from which different types of chairs are created. A Class defines how similar objects are created and an Object is the entity of which is an instance of the Class.

Attribute

  • An Attribute is a variable in a Class that describes the features of that Class.

Method

  • A method is a function that can be called to help describe the functionality of an Object (i.e. string.upper())

Class vs Object

  • A class is a template for creating an object whereas an object is an instance of a class. A class can be described as a logical entity as it contains attributes that describe the features of the object whereas objects are physical entities that are the result of a class' attributes. A class is declared once from where multiple objects can be created.

Constructor

  • A constructor is a subroutine in object oriented programming that is used to create an object from a class. It ensures that the new object is valid by giving the object initial values in its variables.

Logic

Logic programming involves making decisions based on the rules and facts that it is given. It focuses on the use of variables, facts, rules, goals, inference engine (infers using previous knowledge), forward chaining, backward chaining, heuristics.

A logic language has a database of facts and rules, making decisions based on the facts and rules that it is given. Solutions can be arrived at by using forward or backward chaining that uses these rules and facts. Logic languages try to simulate the operations of the brain where it makes decisions based on the rules.

Functional

Functional programming focuses on the use of functions to create programs. By writing programs that rely on functions instead of individual statements, we can build software in a way that emphasises clarity, reusability, and predictability. In the functional programming paradigm, the emphasis is on expressing computations as the evaluation of functions, treating them as fundamental building blocks.

This approach encourages a style of coding where functions are designed to take inputs and produce outputs without altering any external state or relying on variables outside their scope. This makes it easier to understand and reason about the behaviour of functions, leading to more maintainable and bug-resistant code.

 

Emerging Technologies

The increasing speed of technology has allowed programming languages to remove the programmer further away from machine code. Programming tools remove the need to interact with low-level CPU processes. Now, software development is more of an intuitive process.

Mobile technology has increased the need to use different paradigms. Different paradigms are able to compartmentalise code and add new functionality easily. Different architectures (i.e. quantum computers) may work more efficiently with declarative paradigms compared to imperative. Paradigms may be suited to more logical human based processes.

 

Paradigm Strengths Weaknesses
Imperative
  • Efficient
  • Close to the machine hardware
  • Popular
  • Familiar
  • Makes debugging harder
  • Abstraction is more limited
  • Order is crucial, which doesn't always suit itself to problems
  • Code is not ideal for re-use
Object-Oriented
  • Very easy to re-use code and extend it
  • High degree of modularity (easier to understand and maintain)
  • Inheritance saves the re-rewriting of intermitted attributes that are already defined in classes and subclasses
  • It only benefits problems with the need for re-usable code and those that are not sequentially driven
Logic
  • The system solves the problem, so the programming steps themselves are kept to a minimum
  • Proving the validity of a given program is simple
  • Difficult to code complex programs
Functional
  • Focus on high-level design
  • Flexible and reusable
  • Easier to test and debug
  • Easily understood by a human as the code is clear and concise
  • Used less than other paradigms (usually in combination with other paradigms)
  • More memory usage
  • Less expertise and tools that support this paradigm

Classes

Attributes and Methods

Attributes are variables that store data, while methods are functions that perform actions on the data. These are defined within the blueprint of a class. 

Objects

An object is a self-contained unit that consists of attributes and methods from a class that can be used in the program. These objects are instances of classes (i.e. objects are created from classes).
