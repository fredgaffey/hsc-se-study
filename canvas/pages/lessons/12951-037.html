  Learning Intention and Success Criteria

Learning Intention - Students will:

  • Understand the use and purpose of various modelling tools in system development to visually represent data, processes, and structures for better planning and communication.

Success Criteria - Students can:

  • Create data flow diagrams to map the flow of data through a system.
  • Design structure charts to outline the hierarchy and relationships between system modules.
  • Develop a data dictionary to standardise data usage and definitions.
  • Construct class diagrams to represent object-oriented relationships.
  • Utilise storyboards to map out user navigation and interface design.
  • Apply decision trees to document and analyse decision-making processes.

  Content

Modelling tools play a critical role in software development by helping teams visualise, organise, and document different components of a system before the actual coding begins. These tools provide a blueprint that guides the development process, ensuring that all stakeholders have a clear understanding of how the system will function. Different modelling tools serve different purposes, whether it's for mapping out data flow, visualising system structures, or documenting class relationships.

 

Data Flow Diagrams

Recall that a Data Flow Diagram (DFD) is a graphical representation of how data moves through a system. It focuses on the flow of information, where the data comes from, how it is processed, and where it is stored. DFDs are widely used during the planning stages of a project to ensure a shared understanding of how data is handled.

Key components of a DFD:

  • Processes: Represented by circles or rounded rectangles, these are the activities that transform incoming data into outgoing data.
  • Data Stores: Shown as open-ended rectangles, these are places where data is stored within the system.
  • Data Flows: Represented by arrows, these indicate the movement of data between processes, data stores, and external entities.
  • External Entities: Represented by squares, these are outside systems or users that interact with the system by sending or receiving data.

Structure Charts

A structure chart is an abstracted graphical representation of a software system by showing the separate modules or subroutines that comprise the system and their relationship to each other.

They are represented as a hierarchical diagram, where the top level represents the system as a whole, and each subsequent level represents increasingly detailed and refined components of the system. Each component in the structure chart is represented by a rectangular box, and the relationships between components are shown by lines connecting the boxes.

Structure charts are particularly useful for breaking down a large and complex system into smaller, more manageable pieces, and for identifying the relationships and dependencies between those pieces.

Further refinement for each of the lower-level subroutines can be shown in a separate structure chart, using the same name as the subroutine that you are refining in the main structure chart.

The chart is read from top to bottom, with component modules or subroutines on successively lower levels, indicating these modules or subroutines are called by the module or subroutine above.

For all modules or subroutines called by a single module or subroutine, the diagram is read from left to right to show the order of execution.

Data Dictionary

A Data Dictionary is a centralised repository of information about the data within a system. It defines the data elements, their meanings, formats, relationships, and any restrictions or rules. The data dictionary ensures consistency in how data is used across the project.

 

In this course, the following metadata is required in the columns of a data dictionary:

  • Data Item: The name of the variable
  • Data Type: The data type of the variable (i.e. integer, string, boolean, float)
  • Format: The general input/output mask of the variable (i.e. XXXXXX for a 6 character string
  • Number of Bytes for Storage: Number of bytes required to store data the variable (i.e. 4 bytes for an integer
  • Size for Display: Number of characters required to display the variable when printed (i.e. 10 for the date 01/05/2021
  • Description: Describes the purpose and use of the variable
  • Example: An example of data that can be stored in the variabl
  • Validation: Checks that have been put in place (i.e. IF statements) that are used to ensure data integrity (i.e. there are only 12 months in a year)

Class Diagrams

A Class Diagram is a type of Unified Modeling Language (UML) diagram that illustrates the structure of a system by showing its classes, attributes, methods, and relationships. Class diagrams are particularly useful in object-oriented programming as they map out how different objects (or classes) interact within the system.

Key components of a Class Diagram:

  • Classes: Represented by rectangles, each class has attributes (properties) and methods (functions) inside the box.
  • Relationships: Lines or arrows between classes indicate how they are connected (e.g., inheritance, association, or dependency).

 

The basic building blocks of a class diagrams are Classes, which are represented as a rectangle, divided into three parts:

  • The class' name
  • Attributes of the class, with the type of the attribute is specified with a colon and then the type.
  • Methods that the class implements, with the parameters in parenthesis and then the return type specified after a colon

 

In a class diagram we can create many classes and then represent their structure by specifying relationships between them. These may include:

Storyboards

A Storyboard is a visual tool used primarily in user interface (UI) and user experience (UX) design to show how users will navigate through a system. Storyboards consist of a series of drawings or screenshots that represent key screens and interactions within an application, allowing designers to map out the user journey.

Key components of a Storyboard:

  • Screens: Visual representations of the different interfaces the user interacts with.
  • User Actions: Descriptions of what the user does on each screen (e.g., click a button, fill out a form).
  • Transitions: Arrows or lines showing how users move from one screen to another.
